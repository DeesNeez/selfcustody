The card that lost its words

On the dashboard, a pending block slides into the confirmed slot every time the network finds a block. On iPhones, it used to arrive blank — border, glow and background all present, every word gone. This is how it was found.

Try it yourself

A block arrives roughly every ten minutes, which is a miserable way to debug an animation. So the demo below invents one on demand.

Fire a block → The real dashboard, plus a button that confirms a simulated block instantly and a log watching whether the card's text survives.

The symptom

The card kept its orange border, its glow, and its animated background. It lost the height, the fee range, the transaction count — and also Transactions and Lowest, two labels that never change during the transition. That detail mattered more than it looked: those labels were not part of the text crossfade, so whatever was hiding them was not the crossfade. It ruled out the first theory before any code was written.

It only happened on iOS Safari. Narrowing a desktop browser to phone width never reproduced it, which meant the cause was the engine, not the layout.

Three wrong answers

Each theory got its own test page, and each page passed — which is how the theories were eliminated rather than argued about.

Exhibit A — the overlay → Was the card's opaque ::after overlay painting above the text? Eight variants. All readable. No. Exhibit B — the layout animation → Was animating width, flex-basis and padding-inline collapsing the content box? Four variants, with measurements. All readable, all interpolating correctly. No.

A scripted probe on the real page agreed: through the whole 1.4 second flight it reported every line present, opaque and correctly sized. That turned out to be the most misleading evidence of the lot — getComputedStyle reads intent, not pixels. A browser that fails to paint a layer still reports opacity: 1. The probe was blind to exactly the class of bug this was.

The mistake

Every test so far had checked one ingredient at a time. The overlay test used a card that never moved. The movement test used a card with no overlay. The bug needed both at once, so each individual test passed and the real cause slipped between them.

Exhibit C — both together → The card moves while an opaque overlay fades in over it. Five variants. This is the one that reproduced it.

The result

VariantResult
A — the site as it wasblank
B — isolation: isolate on the cardblank
C — text promoted with translateZ(0)readable
D — overlay as a real element, not ::afterblank
E — overlay, but no layout animationblank

E is the one that explains it. With the layout animation removed the card still went blank, so width and padding were never involved — movement plus an opaque overlay is enough on its own. B is the useful failure: isolation: isolate changes nothing, because the card already carries z-index: 3 during the flight and therefore already forms a stacking context. And D shows it is not a pseudo-element quirk; a real child element fails identically.

WebKit composites the moving card and paints the opaque overlay above the text inside that layer, whatever z-index says. Only lifting the text into a layer of its own wins.

The fix

.sc-blocks.is-confirming .sc-block-pending > * {
  transform: translateZ(0);
}

Scoped to the flight, not applied everywhere. The landed card's overlay animates over a stationary card and composites correctly, so there is no reason to hold a promoted layer for every line of all sixteen cards for the sake of the one that moves.

What it cost to find

Three confident wrong diagnoses, four throwaway test pages, and one probe that measured the wrong thing convincingly. The step that actually worked was building a test that could fail — and when it finally did, naming the fix took one more page and about a minute.
